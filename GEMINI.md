# Конституция репозитория

Этот файл — источник правды об архитектуре. Агенты обязаны ему следовать.
Правило приоритета: **этот файл > привычки модели**. Если задача требует нарушить
инвариант — не нарушай, останови работу и напиши `ESCALATE: <причина>`.

Ссылки на детали: @docs/acceptance-contract.md

---

## 1. Как устроен репозиторий

pnpm workspaces + turborepo.

```
apps/
  web/            Next.js (App Router), FSD внутри src/
  admin/          Next.js, FSD
  api-gateway/    Fastify — публичный BFF
  svc-*/          Nest.js микросервисы (svc-billing, svc-notify, ...)
packages/
  contracts/      zod-схемы DTO + типы Kafka-событий. Единственный источник правды межсервисных контрактов
  db/             Prisma schema, клиент, миграции
  ui/             дизайн-система (чистые компоненты, без бизнес-логики)
  config/         eslint/tsconfig/vitest пресеты
  utils/          чистые функции без побочных эффектов и без импортов из app-слоёв
```

Команды: `pnpm turbo run <task> --filter=<pkg>`. Задачи: `lint`, `typecheck`, `test`, `test:e2e`, `build`.

## 2. Инварианты — нарушать нельзя

### 2.1 Границы зависимостей
- `packages/*` **никогда** не импортирует из `apps/*`.
- `packages/utils` и `packages/ui` не импортируют `packages/db` и `packages/contracts`.
- Сервисы (`apps/svc-*`) не импортируют друг друга напрямую — только через `packages/contracts` + Kafka/HTTP.
- Прямой импорт `@prisma/client` разрешён **только** внутри `packages/db` и слоя репозиториев сервиса. Хендлеры/контроллеры/UI работают с доменными типами.
- Новая зависимость между воркспейсами = изменение архитектуры. Требует явного разрешения в контракте задачи.

### 2.2 FSD на фронте (`apps/web`, `apps/admin`)
Порядок слоёв, импорт **только вниз**:
`app → processes → pages → widgets → features → entities → shared`

- Слой не импортирует себя же и ничего выше.
- Кросс-слайсовый импорт — **только через публичный API слайса** (`index.ts`). Импорт во внутренности слайса (`features/x/ui/Button`) запрещён.
- Бизнес-логика не живёт в `shared` и не живёт в компонентах `ui`.
- Серверные компоненты Next не импортируют клиентские хуки; граница `'use client'` проводится как можно ниже по дереву.

### 2.3 База (Prisma / PostgreSQL)
- Миграции **иммутабельны**. Применённую миграцию не редактируют — только новая поверх.
- `prisma migrate reset`, `db push` и `DROP` запрещены везде, кроме локальной разработки. В CI/staging/prod — только `migrate deploy`.
- Разрушающие изменения (drop column, rename, сужение типа, добавление NOT NULL без default) идут **двухфазно**: сначала расширение схемы + двойная запись, потом отдельным релизом удаление старого.
- Каждый внешний ключ и каждое поле, по которому фильтруют или сортируют, имеет индекс. Нет индекса — обоснуй в PR.
- Сырой SQL (`$queryRaw`) — только с параметризацией и комментарием почему ORM не подошёл. Конкатенация строк в SQL запрещена.
- Транзакции: любая операция, меняющая больше одной таблицы согласованно, обёрнута в `$transaction`.
- N+1 — дефект. Связи грузятся через `include`/`select`, батчами или dataloader'ом.

### 2.4 Kafka / события
- Схемы событий живут в `packages/contracts`. Публиковать событие, которого там нет, нельзя.
- События **иммутабельны и версионируются**: `user.created.v1`. Меняешь форму — заводишь `v2`, старую версию продолжаешь поддерживать до вывода всех консьюмеров.
- В событии допустимо только добавление опциональных полей. Удаление и смена типа поля — новая версия.
- Консьюмер идемпотентен: обработка одного и того же `eventId` дважды не меняет результат.
- Обязательны `eventId`, `occurredAt`, `correlationId`, `version` в конверте.
- Ошибки обработки уходят в DLQ, не роняют консьюмера молча.

### 2.5 Redis
- Ключи в неймспейсе: `<app>:<entity>:<id>[:<variant>]`.
- **TTL обязателен всегда.** Ключ без TTL — дефект, кроме явно документированных случаев.
- Redis — кэш и координация, не источник правды. Потеря Redis не должна приводить к потере данных.
- Инвалидация пишется одновременно с записью в кэш, а не «потом».

### 2.6 HTTP-слой (Fastify / Nest)
- Валидация входа на границе: zod-схемы из `packages/contracts`. Невалидированный `req.body` в бизнес-логику не попадает.
- Контроллер тонкий: разобрал вход → дёрнул сервис → отдал ответ. Бизнес-правил в контроллере нет.
- Ошибки — типизированные доменные классы, не строки и не голые `Error`. Маппинг доменной ошибки в HTTP-код происходит в одном месте.
- Каждый эндпоинт: аутентификация явная (в т.ч. явное «публичный»), таймаут, и трассируемый `correlationId`.
- Никаких сырых секретов в коде и логах. Секрет читается из конфига один раз при старте и валидируется.

### 2.7 TypeScript
- `strict: true`. `any` запрещён — используй `unknown` + сужение.
- `as` только с комментарием, объясняющим почему компилятор не может вывести тип. `as any` запрещён.
- `@ts-ignore` запрещён; `@ts-expect-error` — только с описанием и ссылкой на issue.
- Не-null assertion `!` — только там, где инвариант доказан строкой выше.
- Публичный API пакета типизирован явно, без вывода типов через границу пакета.
- Никаких дефолт-экспортов, кроме требуемых фреймворком (страницы Next).

## 3. SOLID / KISS / DRY — практическая трактовка

Это правила про **изменяемость**, а не про красоту. Применяй так:

- **SRP** — у модуля одна причина меняться. Если файл правится и при смене бизнес-правила, и при смене формата хранения — он делает два дела.
- **OCP** — расширяй новым кодом, а не разрастающимся `switch`. Но не строй точки расширения «на будущее»: пока варианта два, `if` честнее фабрики.
- **LSP** — реализация интерфейса не сужает контракт: не кидает новых типов ошибок и не требует большего.
- **ISP** — сервис зависит от узкого порта (`interface UserReader`), а не от толстого репозитория целиком. Это же делает тесты дешёвыми.
- **DIP** — домен зависит от абстракции, инфраструктура реализует её. Prisma/Kafka/Redis — детали за портами.
- **KISS** — самое простое решение, проходящее контракт. Не добавляй слои, абстракции, очереди и кэши, которых задача не требует. Умный код проигрывает скучному.
- **DRY — с правилом трёх.** Дублирование убирается на **третьем** повторении, не на первом. Преждевременная общая абстракция дороже дублирования: два похожих куска, которые дальше расходятся, — это не дубль. DRY про знание, а не про совпадение символов.
- **YAGNI** — не пишем «пригодится потом». Не пригождается.

Приоритет при конфликте: **корректность → читаемость → расширяемость → краткость**.

## 4. Тесты

- Юнит/интеграция — Vitest. E2E — Playwright.
- Тест проверяет **поведение по контракту**, а не реализацию. Не мокай то, что тестируешь; не проверяй вызовы приватных методов.
- Внешние границы (БД, Kafka, HTTP наружу) — testcontainers или фейк на уровне порта. Мок Prisma-клиента целиком — плохой тест.
- Каждое исправление дефекта начинается с падающего теста, воспроизводящего дефект.
- Новый эндпоинт/консьюмер = хотя бы один интеграционный тест на happy path и один на отказ.
- Тесты детерминированы: без `sleep`, без реального времени (инжектируй clock), без зависимости от порядка.

## 5. Критические зоны — только с человеком

Изменения по этим путям **никогда** не мёржатся без ревью человека. Агент, затронувший их, обязан остановиться и написать `ESCALATE`.

## 6. Git и рабочий процесс

- Ветка на задачу: `feat/<TICKET>-<slug>`, `fix/...`, `chore/...`.
- Коммиты Conventional Commits. Один коммит — одно логическое изменение.
- `git push --force` в `main`/`develop` запрещён.
- В PR не попадают: закомментированный код, `console.log`, `TODO` без тикета, неиспользуемые экспорты.
- PR без прохождения контракта задачи не создаётся.

## 7. Go (сервисы в разработке)

Пока в репозитории Go нет. Когда появится:
идиоматичный layout (`cmd/`, `internal/`), ошибки оборачиваются через `fmt.Errorf("...: %w", err)`,
контекст первым аргументом, отсутствие глобального состояния, `golangci-lint` в CI.
Не переносить в Go привычки TypeScript: интерфейсы объявляются на стороне потребителя и держатся узкими.

## 8. Чего агент не делает никогда

- Не отключает правило линтера, чтобы код прошёл. Чинит код.
- Не пишет тест под текущее поведение, чтобы тест позеленел. Чинит поведение.
- Не расширяет объём задачи за пределы контракта. Нашёл смежную проблему — фиксирует в отчёте, не чинит молча.
- Не трогает `pnpm-lock.yaml` руками.
- Не добавляет зависимость, если задача решается стандартной библиотекой или уже установленным пакетом.
- Не удаляет и не переписывает чужие тесты, чтобы прошёл свой код.
